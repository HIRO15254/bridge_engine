骨格の実装方針 (計画からの差分):

- `todo!()` 本体の未使用引数・未使用フィールドの警告は、計画の `let _ = ...` ではなく、各クレートの `lib.rs` に置いた crate レベルの `#![allow(dead_code, unused_variables)]` で抑える (`bridge` ファサードだけは本体があるので不要)。この allow は本体を実装するフェーズ (`todo!("phase N")` の N) で外し、実装後に残る未使用はコードの整理で解消する。
- `const` / `static` 項目はコンパイル時に評価されるため `todo!()` にできない。したがって定数表 `SHAPES`、`CLASSES`、`CLASS_OF`、`ShapeSet` の定数 (`ALL`, `BALANCED`, `SEMI_BALANCED`)、`MAX_HCP`/`MIN_HCP`、`bridge_eval::SUIT` (8192 × 5 のスート表) と、それらが依存する `const fn` (`shape_index`, `Shape::class`, `ShapeSet::from_class` 等) は骨格の時点で完全に実装済みで、単体テスト (`shape.rs`, `tables.rs`) も付いている。フェーズ 1.2 / 2.1 のタスクはこれらの検証を追加するだけで、実装は要らない。

完了条件 (2026-09 改訂、`15-phase4-plan.md` の「完了基準の改訂案」と D20)。[G] は SAYC 自身が生成したオークション (整合したモデル)、[C] はコーパスで測る。どちらも毎回両方を報告する。

- (a) カバレッジ
  - [G] 固定 seed のランダム配牌 1000 本を replay (ナチュラル補完あり) したとき、≥ 80% が全コールシステム (ナチュラル補完も gap も無い)。システムの作者が制御できるカバレッジで、ナチュラル補完が穴の印になるので同語反復ではない。ただし「どんな手でもパス」だけが行の位置 (パスの連鎖や、それを置き換えたシステム停止 `#STOP` / `{stop}`、`06-system.md` §4.5) は穴を隠すので、strict 集計で数える: そうした位置でナチュラルの選択 m_P(h) がパス以外なら、そこで離脱したものとする (`all_system_strict`)。基準は strict の値に適用し、素の値と連鎖なしの値を並べて報告する。
  - [C] コーパスの SAYC 互換オープニング部分集合 (真のオープナーの手が記録されたオープニングの排他領域 X に入る) で、コール単位のシステム解決率 (Exact または Partial) ≥ 80%。[G] と同じ理由で strict 集計で数える: 呼び手のシステムが既定パス (priority ≤ −100 のパス) しか出さない位置の Exact / Partial は解決に数えない (`xtask coverage` の `system_resolution_strict_rate`、除いた数は `resolved_at_default_pass`)。基準は strict の値に適用し、素の値を並べて報告する。
  - オークション単位の全コール Exact 率をコーパス全体・評価用分割・部分集合で報告し、4.1 のベースラインを下回らないこと。
  - `EmptySupport`: 既定モードでコーパスのサンプラー `EmptySupport` 0。strict な支持が空の席数は報告する。
- (b) 再現率
  - [G] 生成オークション 100 本で中央値 ≥ 0.6 (`ConstraintProposal` と方策尤度で重み付け)。
  - [C] コーパスの SAYC 再現可能部分集合 (真の配牌を replay すると記録どおりのオークションになる) で中央値 ≥ 0.6。部分集合の件数も報告する。
  - 旧定義 (コーパス全体、一様提案) の中央値と、コール単位の実配牌での方策一致率も継続性のために報告する。
- (c) 新しいゲート: `policy_mirror` の under-cover 0 かつ exact ≥ 99%、`tightness` 0/0、整合性の gap 起因でない違反 0、`interpret` 12 コール < 10 μs (フェーズ 3 から持ち越し、フェーズ 3 では未達)。

改訂の理由: コーパス (2019 年世界選手権と BBO vugraph) の大半はストロング・クラブや 2/1 とその独自の約束事で競られているのに、SAYC として解釈・replay している。これはモデルの誤指定で、コーパス 100 本中 97 本がシステム上の位置でナチュラルなコールを含み、フェーズ 3 の再現率はどの試作でも解釈にかかわらず 0.0 だった (試作 B は 92/100 で ESS ≥ 30 でも中央値 0)。コーパスだけの閾値は SAYC のカバレッジやサンプラーの質ではなくコーパスのシステム構成を測ってしまう。棄却を許すと ESS の基準も曖昧になり (B の ESS/n 0.906 に対し試行あたり 0.371)、生成 ESS ケースは方策が変わるたびに変わり、いくつかのパラメータが評価スイートそのもので調整されていた。同じ閾値 (80%、0.6、0.5) を整合した集合に適用し、コーパス側の対応物を定義し、両方を必ず報告するという趣旨は保つ。

このフェーズでコードを書いている時間が長いなら L1/L2 の設計が間違っている (増えるべきはデータ)。

### フェーズ 4 の resolve_lenient 調査

最終統合で `resolve_lenient` の使用が 61 / 8,169 コールに増えた原因を切り分けた (wip/p4-len、起点 9ac0b40)。`cargo xtask coverage` には調査用の出力を足した。`COVERAGE_PRINT_LENIENT` を設定すると、lenient に解決したコールごとに次を出す。

- オークション
- 厳密な解決が止まった深さ
- パスと読み替えた相手のコール
- 使われた行 (ファイルと行番号、または停止のパス)

JSON には `resolve_lenient_top50` と 2 つの数を足した (d7fb70d)。フェーズ 4 の最終レビューの修正 (レーン X) で 2 つの定義を次のように改め、3 つ目の数を足した。この節の数は、断りの無い限り改めた定義で測り直したものである。

- `resolve_lenient_entries`: 停止のループの続きでない lenient なコール。続きとは、停止の既定のパス (合成された停止のパス、または優先度 −100 以下のパスの行) に解決し、かつ同じパートナーシップの前の lenient なコールがパスと読み替えた相手のコールを、同じくパスと読み替えたコールである。ほかは全て入口と数える。同じ置き換えを通っても書いた行に解決するコールは、独立した lenient な表の読みなので入口である。
  - d7fb70d の定義は「パートナーシップがそのオークションで初めて lenient に入ったコール」だった。2 本目以降は停止を通るかを確かめずに続きと数えていた。停止の無いシステムでも、置き換えた相手のコールはそのパートナーシップの後のキーに残るので、無競合の表が続けば 2 本目の lenient な読みは起こる。
- `resolve_lenient_eligible_calls`: 厳密な解決が、相手のオープニングより後の、相手のパス以外のコールで止まるコール。lenient の置き換えが効き得るのはこのコールだけである。
- `resolve_lenient_opening_stalls`: 厳密な解決が相手のオープニング (深さ 0) で止まるコール。そこをパスに置き換えたキーはパスで始まり、どの行にも合わない (キーは先頭のパスを除く)。d7fb70d の `resolve_lenient_eligible_calls` はこれを含んでいたので、分けて数える。

既存の `resolve_lenient_calls` と `resolve_lenient_rate` の定義は変えていない。

**原因。** コードの不具合ではない。同じコードで測ると、段階 2 の SAYC は 1、レーン D2 の SAYC は 61 である。厳密な解決の深さはどちらでも変わらない。

増えた分は、レーン D2 が加えた表 (`competing.bml`、`continuations-p12.bml`、`later-rounds-extra.bml`) から来ている。いずれも相手のパスの後の我々のコールを書いた表である。これらの表には、相手のパス以外のコールを受ける `(any)` の兄弟 (`systems/sayc/NOTES.md` #C4) が無かった。そのため相手がそこでビッドやダブルをすると、`resolve_lenient` がそれをパスと読み替え、競合の無いオークション向けの表を当てはめていた。#P7 で 5 → 66 → 1 と直したのと同じ穴である。

`human()` の設定で変えた試験は 1 本である。`policy_weighted_rejection_follows_the_likelihood` は、パスアウトで重み付きの率が重み 1 の率を上回る幅を 0.1 から 0.05 にした。重み 1 の率はどちらのプリセットでも 0.835 で、重み付きの率は仮置きで 0.948、新しい値で 0.931 である。δ が大きくなると差が縮まる。パスアウトでは、システムのコールがパスである席のほぼ全てでナチュラルのコールもパスなので、その手のパスの確率は (1−ε) + ε/n、逸脱としてだけパスする手は (1−ε)δ + ε/n である (始めの合法なコールは n = 36)。比 (1−ε+ε/n) / ((1−ε)δ+ε/n) は仮置きで約 3.3、新しい値で約 2.5 である ((1−δ)/δ の 2.3 と 1.5 は、システムだけがパスする少数の席にしか当てはまらない)。逸脱する席が配牌に 1 つの近似で、重み付きの率は u / (u + (1−u)/比)、u = 0.835 から 0.944 と 0.926 になり、実測の 0.948 と 0.931 に合う。新しい値で見込まれる差は約 0.09 で、0.05 はその約半分を余裕として残す。この試験は当てはめ直しで幅が動かないよう、`human()` を呼ばずにこの値 (ε 0.3404、δ 0.3959) を定数で固定した (`mirror.rs` が δ 0.3 を固定するのと同じ)。重みが尤度そのものであること、ESS < 残った配牌数であることの検査は変えていない (`11-testing.md` §3.3)。再現率 (ii) が 0.875 から 0.8265 に下がるのも、同じく逸脱の片の重みが大きくなったためである。
