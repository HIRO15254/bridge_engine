# 16. 拡張 BML リファレンス (`bridge-system` が受理する方言)

本書は、`crates/bridge-system` のコンパイラ (`COMPILE_REVISION` 9、`IR_FORMAT` 3) が受理する BML (Bridge Bidding Markup Language) の方言の、唯一の正本である。上流の BML (gpaulissen/bml の `bml.py` / `bss.py`) に、フェーズ 3〜4 で加えた拡張 (`#+KEY:` メタ、`{prio:N}` / `{w:X}` / `{stop}` 注釈、`X`/`XX`、`2S/3H`・`4D/H`、`n`・`c`・`j` のレベル、`(any)`/`(bid)`/`(suit)`、`#STOP`、`#ANYORDER`、スート長の比較、…) を含めて、新しいシステムファイルをソースを読まずに書けるように、コードから書き起こした。

- 設計の経緯と内部構造は `06-system.md` にある。本書と `06-system.md` が食い違うときは、コードと本書が正である (既知の食い違いは付録 B)。
- SAYC の実例は `systems/sayc/*.bml` (ルートは `sayc.bml`) にある。
- 本書の `bml` のコードブロックは、`crates/bridge-system/tests/bml_reference.rs` が全て抜き出してコンパイルする (§0.2)。本書の例は「動く」ことが試験で保証されている。

## 0. 読み方

### 0.1 表記

- 「上流」は gpaulissen/bml の Python 実装 (`bml.py` は HTML/LaTeX への変換器、`bss.py` はビディング表の展開器 (BSS 出力)) を指す。
- 「(拡張)」は上流に無い構文・意味、「(上流)」は上流と同じもの。
- 文法は EBNF で書く。`WS` は 1 個以上の空白 (半角スペース)、`WS0` は 0 個以上、`NL` は改行。完全な文法は §9。
- `Lint` の名前は `LintCode` の variant 名 (`IllegalCall` など) で書く。重大度は Error / Warning / Info。一覧は §8。
- 「我々」はシステムの持ち主のパートナーシップ、「相手」は反対側。

### 0.2 本書の例の試験

`crates/bridge-system/tests/bml_reference.rs` は、本書の各コードブロックを情報文字列で区別して扱う。

| 情報文字列 | 意味 |
| --- | --- |
| `bml` | 単独のファイル (`root.bml`) としてコンパイルし、Error の Lint が 0 件であること |
| `bml,should-lint` | 1 行目に `// expect-lint: <Code>` (列 0 の注釈なのでコンパイラは読み飛ばす) を書く。その Lint が出ること、それ以外の Error が出ないこと |
| `bml,file=<path>` | 内容を `<path>` という名前のファイルとして登録し (他のブロックの `#INCLUDE <path>` がこれを読む)、それ自身も `bml` と同じく検査する |

同じ試験は、`LintCode` の全 variant、全ての `#+KEY:`、説明文の語彙表 (`compile/desc/tokens.rs`、`clause.rs`、`recognition.rs` の語の表) の全ての語が本書に書かれていることも確かめる。コードに語や Lint を足したら、本書に足さないと試験が落ちる。

### 0.3 Lint の見方

コンパイルは決して全体としては失敗せず、問題を `Lint` の列として返す。自分のファイルの Lint を見るには、次のようにする (`Lint` の `Display` は `file:line: severity[Code]: message`。`file` は `#INCLUDE` 順のファイル番号で、0 がルート)。

```rust
use bridge_system::{CompileOptions, compile, lexer::FsLoader};

let path = "systems/mine/root.bml";
let text = std::fs::read_to_string(path)?;
let (ir, lints) = compile(path, &text, &FsLoader, &CompileOptions::default());
for lint in &lints {
    println!("{lint}");
}
```

## 1. 範囲と互換性

### 1.1 上流 BML との関係

本方言は、上流 BML 2 (README 2021-07、`bml.py` / `bss.py`) の **ビディング表の部分** の上位互換である。上流の正しいファイルは、次の例外を除き、本コンパイラで同じ展開になる (上流の `test/data/example{1..6}.bml` と期待出力 `.bss` を `tests/bss_oracle.rs` がオラクルとして照合している)。

- 本コンパイラが扱うのは入札の定義だけである。上流の文書機能 (見出し・リスト・段落のフォント記法 `/i/ *b* =mono=`、ディール図、4 列オークション表、パイプ表) は、段落として読み飛ばす (制約にも Lint にも影響しない)。
- `#HIDE` (上流: 表を BSS にだけ出す) は印を記録するだけで、表は常にコンパイルする。

拡張は、D16 (`13-decisions.md`) の原則「上流ツールが無視するか説明文として読む形で書く」に従う。ただしコールトークンと表の指示子は木の構造そのものなので、この原則を守れない拡張がある (次節の表の「非互換」)。その場合は `NonStandardToken` (Info) などで著者に見えるようにしている。

### 1.2 拡張の一覧と上流ツールでの扱い

| 拡張 | 形 | 本書 | 上流ツール (`bml.py` / `bss.py`) での扱い | 本コンパイラの Lint |
| --- | --- | --- | --- | --- |
| メタキー | `#+STRENGTH:` `#+NATURAL:` `#+DISTPOINTS:` `#+TIEBREAK:` `#+BALANCED:` `#+CONVENTION:` `#+RECOGNITION:` `#+VERSION:` | §6.5 | 無視 (任意の `\w+` キーを `meta` に入れるだけ) | 値の誤り: `UnknownDirective` (Warning) |
| 優先度 | 説明文中の `{prio:N}` | §6.1 | 説明文の一部として表示される | なし |
| 枝の重み | 説明文中の `{w:X}` | §6.2 | 説明文の一部として表示される | なし |
| システム停止 (行) | 説明文中の `{stop}` | §6.3、§7.7 | 説明文の一部として表示される | `StopUnderForcing` (Warning) |
| システム停止 (指示子) | 表の中の行 `#STOP` | §2.10、§7.7 | 非互換: 未知の行 (表の行として読めず、上流では誤読か失敗) | 同上。置き場所の誤り: `UnknownDirective` |
| 変数の順序を外す | 表の中の行 `#ANYORDER` | §2.10、§4.2 | 非互換: 未知の行。展開は順序つき (本コンパイラの展開の部分集合) になる | `AnyOrderWithoutVariables` (Info) |
| 裸のダブル・リダブル | `X`、`XX` | §4.1 | 非互換: `bid_type()` が読めない | `NonStandardToken` (Info) |
| 代替コール | `2S/3H`、`4D/H` | §4.5 | 非互換: `2S/3H` は末尾 2 文字だけ黙って残り、`4D/H` はクラッシュ | `NonStandardToken` (Info) |
| 全レベル | `nX`、`(nX)`、`nS` | §4.3 | 非互換: クラッシュ | `NonStandardToken` (Info)、候補が 8 を超えると `WideWildcard` (Info) |
| 相対レベル | `cS`、`jY`、`cM` | §4.3 | 非互換: レベルとして読まない | `NonStandardToken` (Info)、`LevelWithoutAnchor` (Error)、`NoSufficientLevel` (Info) |
| 小文字の変数 | `1x`、`2y`、`3z` | §4.2 | 非互換 | `NonStandardToken` (Info) |
| 相手のコールの類 | `(any)`、`(bid)`、`(suit)` | §4.6 | 非互換 | `NonStandardToken` (Info) |
| アラート印 | 説明文の先頭の `!` (直後が小文字の `c d h s` でないとき) | §3.6 | 説明文の一部として表示される (上流の著者の慣例) | なし |
| 説明文中の `#` | `5+#`、`0--1#` | §5.3 | 説明文の一部として表示される | なし |
| スート長の比較 | `!s>=!h`、`M>oM` | §5.4.12 | 説明文の一部として表示される | なし |
| 説明文の語彙全体 | `12--14 hcp, 5+!s, GF` など | §5 | 上流は説明文を解釈しない (表示するだけ) | `UnrecognizedFragment` ほか |

「非互換」の拡張を使ったファイルは、上流ツールでは正しく処理されない。上流との可搬性が要るファイルでは、`NonStandardToken` (Info) の出る行を避けるか、上流用の別ファイルに書き分ける。

### 1.3 Python 実装との意図的な差分

上流の正しいファイルの扱いでも、次の点は意図的に上流と違う。

1. **インデントの単位**。上流は固定の単位 (既定 2) を強制し、違反は `IndentationError` で止まる。本コンパイラは表ごとに最初の親子の差を単位とし、違う差は `IndentationMismatch` (Warning) を出して最も近い浅い行の子にする (§3.2)。
2. **末尾記号の無い履歴行の後の列 0 の行**。上流は新しいオープニングとして読む。本コンパイラは著者の意図どおり履歴の子として読み、`ColumnZeroContinuation` (Info) を出す (§3.4)。
3. **Exact 行はパターン行に勝つ**。上流 README の意図どおり、兄弟の間では Exact 行を行順に先に展開し、パターン行はその後に展開する (`bss.py` は実際には行順)。同じコールを作るパターン行は `ShadowedByExact` (Info) で捨てる (§4.8)。
4. **非標準のトークンを受理する**。`2S/3H`、`4D/H`、`nX`、`X`/`XX`、小文字の `x/y/z` (上流: クラッシュか誤読)。それぞれ `NonStandardToken` (Info) を付ける。
5. **エラーは行単位**。読めない行はその行と部分木だけを捨て、ファイルの残りはコンパイルする (§3.7)。
6. **説明文をコンパイルする**。上流は説明文を表示するだけだが、本コンパイラは説明文を手の制約 (`HandConstraint`) にコンパイルする (§5)。
7. **席は条件**。`#SEAT` はオープナーの席位置の条件で、先頭のパスは経路に含めない (上流の BSS も同じ符号化。D17)。
8. **同一条件の再定義で空の説明を埋める**。上流の「後の定義は空の説明を埋めるときだけ効く」を、席・バル条件の包含関係にまで広げる (§4.8)。

## 2. ファイル構造

### 2.1 行、段落、空白

- ファイルは行の列である。行末は `\n` か `\r\n` (Rust の `str::lines` で分ける)。
- **段落** は 1 行以上の空行 (空白だけの行を含む) で区切られた行の塊である。段落の種類 (§2.2) は段落の最初の行で決まる。
- 字下げは **半角スペースだけ** を数える。タブは字下げに数えない (タブで字下げした行は列 0 の行として読まれ、トークンの一部にもなる)。字下げにはスペースを使う。
- コールトークンと説明文は **最初のスペース** で区切る (タブではない)。

### 2.2 段落の分類

段落の最初の行 (先頭の空白を除く) を次の順に調べ、最初に当てはまる種類とする (上流の順序に合わせてある)。

| 順 | 条件 | 種類 |
| --- | --- | --- |
| 1 | `*` で始まる | 見出し |
| 2 | `-` で始まる | 箇条書き |
| 3 | `#VUL` で始まる | バル条件 (§2.7) |
| 4 | `#SEAT` で始まる | 席条件 (§2.6) |
| 5 | 数字の列の直後に `.` があり、その後が空白か行末 | 番号付き箇条書き |
| 6 | 最初の語 (空白までの文字列) 全体がコールトークン (§4) か履歴 (§3.4) として読める。ただし相対レベル (`c`/`j`) のトークンを除く | ビディング表 |
| 7 | `#+` の直後が英数字か `_` | メタ行 (§6.5) |
| 8 | `#` で始まる | 指示子つきのビディング表 (§2.10) |
| 9 | それ以外 | 地の文の段落 |

**落とし穴**: 規則 6 は「最初の語がコールとして読めるか」だけを見る。地の文の段落が `P`、`D`、`R`、`X`、`XX`、`1C`、`2NT`、`(1H)` などの語、あるいは **`any`、`bid`、`suit`** (相手の類のトークン §4.6 が括弧なしでも読めるため) で始まると、その段落はビディング表として読まれる。地の文をこれらの語で始めないこと (例: 「bid ...」ではなく「A bid ...」)。逆に、相対レベルの行 (`cS = ...`) で始まる段落は表にならず地の文になり、`UnknownCallToken` (Warning) が出る (§4.3)。

### 2.3 注釈 (コメント)

- **列 0 の `//`** で始まる行だけが注釈で、読み込みの段階で行ごと消える (段落の区切りにもならない)。
- 字下げした `//` や、行の途中の `//` は注釈ではない (表の中では説明文の一部、地の文では本文)。

```bml
// This whole line is dropped before paragraphs are formed.
1C = 12--21 hcp, 3+!c
// A column-0 comment between two rows keeps them in one table.
1D = 12--21 hcp, 3+!d
```

### 2.4 `#INCLUDE`

```text
include = WS0 , "#" , WS0 , "INCLUDE" , WS0 , PATH , [ WS , { CHAR } ] , NL ;
```

- 上流の正規表現 `^\s*#\s*INCLUDE\s*(\S+)` と同じく、字下げした `#INCLUDE` や `# INCLUDE` も受理し、キーワードの後の最初の語だけがパスで、残りは無視する。
- **パスは、包含する側のファイルのディレクトリからの相対パス** (絶対パスも可)。`/` と `\` はどちらも区切りとして読み、`.` と `..` を正規化する。Windows の `C:` のドライブ接頭辞は根として扱う。
- 包含したファイルの行は `#INCLUDE` の行の位置に差し込まれ、**前後に空行が 1 行ずつ入る** (上流の `'\n' + text + '\n'` と同じ)。したがって包含されたファイルは必ず自分の段落で始まり、自分の段落で終わる。連続する 2 つの `#INCLUDE` の表が 1 つの表に融合することは無い。
- `#SEAT` / `#VUL` の状態 (§2.6) とクリップボード (§2.9) はファイルの境を越えて引き継がれる (全ファイルを 1 本の行の列として読むため)。
- 見つからないファイルは `IncludeNotFound` (Warning) を出してその行を捨てる。循環か 16 段を超える入れ子は `IncludeCycle` (Error)。
- 読み込みは `SourceLoader` を通る。`FsLoader` はファイルシステムから、`MemLoader` はメモリ上の `(パス, テキスト)` の表から読む (wasm などファイルシステムの無い環境用)。

```bml,file=parts/openings.bml
1C = 12--21 hcp, 3+!c
1D = 12--21 hcp, 3+!d
```

```bml
#+TITLE: Include demo

#INCLUDE parts/openings.bml

1C-
1H = 6+ hcp, 4+!h
```

### 2.5 見出し、箇条書き、地の文

- 見出し (`*`、`**`、…)、箇条書き (`-`)、番号付き箇条書き (`1.`)、地の文の段落は、コンパイラにとっては文書の飾りである。展開にも制約にも影響しない (`BmlFile.blocks` に残るだけ)。
- 箇条書きの 2 行目以降で記号の無い行は、直前の項目の続きになる。
- 見出しは `#SEAT` / `#VUL` の状態をリセットしない。

### 2.6 `#SEAT` (オープナーの席)

```text
seat = "#SEAT" , WS , ( "0" | "1" | "2" | "3" | "4" | "12" | "34" ) ;
```

- `#SEAT s` は、それ以降の全ての表 (次の `#SEAT` まで、`#INCLUDE` の境を越えて) に付く条件で、**オープニングビッドが行われた席の位置** を指す。先頭のパスが k 個ならオープナーの位置は k + 1 (1 = ディーラーがオープン)。
- `0` = どこでも (既定)、`1`〜`4` = その位置、`12` = 1 か 2、`34` = 3 か 4。
- 先頭のパスは経路に含めない。`#SEAT 34` の表に `1H-` と書けば、「3 席目か 4 席目でオープンした 1H の後」を意味する (パスを書かない)。
- 相手のオープニングの表 (`(1H)-` で始まる表) でも、条件は「その相手のオープナーの位置」である。
- 読めない値は `UnknownDirective` (Warning) を出し `0` として扱う。
- `#SEAT` は段落 (空行で区切った 1 行) として書く。表の中に書いても効かない (表の中の未知の指示子として `UnknownDirective`)。

### 2.7 `#VUL` (バルネラビリティ)

```text
vul = "#VUL" , WS , TRI , TRI ;       TRI = "Y" | "N" | "0" ;
```

- 1 文字目が我々、2 文字目が相手のバル。`Y` = バル、`N` = ノンバル、`0` = どちらでも。例: `#VUL YN` は我々だけバル、`#VUL 0Y` は相手がバル、`#VUL 00` で解除。
- 以降の全ての表に付く (§2.6 と同じく粘着的)。読めない値は `UnknownDirective` (Warning) で `00`。

同じ位置に条件の違う定義があるときの選び方は §4.8 と §7.1。

```bml
1H = 12--21 hcp, 5+!h

#SEAT 34

1H-
2C = 10--11 hcp, 5+!c, 3+!h

#SEAT 0

#VUL YN

1H-
3H = 10--12 hcp, 4+!h

#VUL 00
```

### 2.8 メタ行

`#+KEY: value` の段落。§6.5 で詳述する。1 つの段落に何行でも書け、`#+` で始まらない行や `:` の無い行は `UnknownDirective` (Warning)。

### 2.9 クリップボード: `#COPY`、`#CUT`、`#PASTE`

表の一部を名前付きで保存し、別の場所へ貼り付ける (上流と同じ。テキストの置換である)。

| 指示子 | 意味 |
| --- | --- |
| `#COPY name` … `#ENDCOPY` | 間の行をクリップボード `name` に保存し、**その場にも残す** |
| `#CUT name` … `#ENDCUT` | 間の行をクリップボード `name` に保存し、その場からは **取り除く**。段落全体が `#CUT` … `#ENDCUT` なら、表を作らないクリップボード専用の段落になる |
| `#PASTE name [tgt=rep …]` | クリップボード `name` の行をここに差し込む。各行の先頭に `#PASTE` 行の字下げを付け、`tgt=rep` の置換を **書いた順に** 単純な文字列置換として行う |

- 保存する本文は、`#COPY` / `#CUT` 行の字下げの分だけ左へずらす。貼るときに `#PASTE` 行の字下げを足すので、クリップボードの本文は列 0 基準で書き、貼る側で深さを決める。
- 名前の再定義は、**後の定義がそれ以降の貼り付けに効く** (上流の辞書と同じ)。
- 貼った本文の中の `#PASTE` も展開する (字下げは積み重なる)。16 段を超える入れ子 (自分自身を貼るクリップボード) は `UnknownDirective` (Warning) で打ち切る。
- 無い名前の `#PASTE` は `PasteUnknownName` (Warning)。`#ENDCUT` / `#ENDCOPY` の無い開始は `UnknownDirective` (Warning) で、その開始行だけを捨てる。
- 処理の順は、段落ごとに `#CUT` を全部抜き出し、次に `#COPY`、最後に `#PASTE` を展開する。したがって同じ段落の中でも、`#PASTE` は同じ段落の後ろにある `#CUT` の本文を使える。
- 置換は字句の置換なので、`\R=D` のように、本文に他に現れない印を使う (上流の慣例は `\` で始まる印)。印は語の境界を問わず全ての出現を置き換える。
- 貼られた行の位置 (`Span`) は `#PASTE` の行を指し、`pasted_from` にクリップボード名と本文の行番号が入る。

```bml
#CUT transfer
2\R = !TRF, 5+\M
  2\S = 2+\M
#ENDCUT

1N = 15--17 hcp, bal

1N-
2C = !STAY, 8+ hcp
#PASTE transfer \R=D \M=!h \S=H
#PASTE transfer \R=H \M=!s \S=S
```

1 つ目の `#PASTE` は `2D = !TRF, 5+!h` とその子 `  2H = 2+!h` を、2 つ目は `2H = !TRF, 5+!s` と `  2S = 2+!s` を差し込む。置換は本文の全ての出現に効くので、コールトークンに入れる印 (`\S` はストレインの文字) と説明文に入れる印 (`\M` はスート記号) を分けている。同じ印を両方に使うと、例えば子の行が `2!h` になり、コールトークンとして読めずに `UnknownCallToken` (Warning) になる。

### 2.10 表の中の指示子

ビディング表の段落の中 (行と行の間、または最初の行の前) に、`#` で始まる 1 行の指示子を書ける。前後の空白は無視する。

| 指示子 | 意味 | 由来 |
| --- | --- | --- |
| `#HIDE` | 表に「隠す」印を付ける (`BidTable.hidden`)。コンパイルには影響しない | 上流 (BSS にだけ出す) |
| `#BIDTABLE` | 何もしない (上流では段落を表として扱わせる。本コンパイラは段落の最初の行が `#` なら表として読むので不要) | 上流 |
| `#COPY` / `#CUT` / `#PASTE` / `#ENDCOPY` / `#ENDCUT` | §2.9 | 上流 |
| `#STOP` | システム停止。行の子の位置 (その行より深い字下げ) に書くとその行の後に、表の最上位 (字下げ 0) に書くと表の履歴の位置に停止を置く (§7.7) | 拡張 |
| `#ANYORDER` | その表全体で、新しく束縛する `X`/`Y`/`Z` の `X < Y < Z` の順序を外す (§4.2)。表のどこに書いても表全体に効く | 拡張 |
| その他の `#…` | `UnknownDirective` (Warning) を出して、その行を無視する | |

- `#STOP` と `#ANYORDER` は、表と同じ段落に書く。空行で区切った独立の段落 (`#SEAT` のような書き方) に書くと表を名指さないので効かず、`UnknownDirective` (Warning) が出る。
- 履歴の無い表の最上位の `#STOP` は位置を名指さないので、`UnknownDirective` (Warning) を出して無視する。

```bml
1C = 12--21 hcp, 3+!c

1C-
1H = 6+ hcp, 4+!h
  #STOP
1N = 6--10 hcp
2C = 11+ hcp, 5+!c
P = {prio:-100} {stop} any hand

1C-2C-
#STOP
2N = 13--15 hcp, bal
```

## 3. ビディング表

### 3.1 行

```text
row      = WS0 , calltok , [ WS , [ "=" , WS0 ] , description ] , NL , { contline } ;
```

- 行は「字下げ、コールトークン、空白、説明文」である。コールトークンの直後の `=` は省略できる糖衣 (`1C = 12+ hcp` と `1C  12+ hcp` は同じ)。
- コールトークンは行頭の空白の後から **最初のスペースまで** の文字列全体で、その全体が §4 の `calltok` として読めなければならない (読めなければ §3.7)。
- 説明文の先頭の `!` はアラート印 (§3.6)。
- 説明文は省略できる (空の説明: 制約なし、`EmptyDescription` (Info))。

### 3.2 字下げと木

- 字下げが行の木を作る。ある行より字下げの深い次の行はその子、同じか浅い行はその行を閉じて、字下げがより浅い祖先の子 (祖先が無ければ表の最上位の行) になる。
- **子の行は、親の行が表すコールの後の、次の手番のコール** を表す (相手の手番を挟む場合は暗黙のパス §3.5)。
- **字下げの単位は表ごとに推定する**: 表の中で最初に現れた「親から子への字下げの差」がその表の単位である。以後、差が単位と違う子は `IndentationMismatch` (Warning) を出すが、捨てずに最も近い浅い行の子にする。単位は 2 でも 4 でもよいが、1 つの表の中では揃える。
- 表の最上位の行どうしは字下げが違ってもよい (単位の検査は親子の間だけ)。

### 3.3 継続行

- **前の行の説明文が始まった桁と同じ字下げ** の行は、その説明文の続きになる (`\n` で連結。行末の空白は落とす)。
- この規則の帰結として、子の行を親の説明文と同じ桁から始めることはできない (続きとして読まれる)。子は説明文より浅く字下げする。
- コールトークンだけで説明文の無い行 (トークンの後に空白も `=` も無い行) には続きが無い。
- 継続行の中の列挙 (`a)`、`1)` …) は選言になる (§5.3)。

```bml
1C = one of:
     a) 12--14 hcp, bal
     b) 15+ hcp, 5+!c
  1D = 0--7 hcp
```

ここで `a)` と `b)` の行は `1C` の説明の続き (説明文が 5 桁目から始まり、続きも 5 桁目)、`1D` は字下げ 2 の子である。

### 3.4 履歴行

表の **最初の行** のコールトークンが `-` か `;` を含むなら、その行は **履歴行** である。

```text
history-row = WS0 , seq , [ WS , [ "=" , WS0 ] , description ] , NL , { contline } ;
seq         = calltok , { ( "-" | ";" ) , calltok } , { "-" | ";" } ;
```

- 履歴行は、表の行が続く位置までのオークション (オープニングから) を書く: `1N-2C;`、`1C-`、`1C---`、`1C-1D;`、`(1NT)---`、`(1N)-P-(P)---`、`1C-(1D)-`。区切りは `-` でも `;` でもよく、末尾の `-`/`;` の個数は見た目だけである (区切りを 2 つ続けられるのは末尾だけ)。
- 表の行は全て、履歴の最後のコールの子になる (表の最上位の行 = 履歴の後の次の手番のコール)。
- 履歴の途中の暗黙パスは §3.5 の規則で補う (`1N-2C` は `1N (P) 2C`)。
- 履歴行に書いた説明文は **履歴の最後のコール** のものになる。
- 履歴の中の変数 (`(1X)-`、`1M-2N-`) はそこで束縛され、表の全ての行から見える。変数が複数の候補を持てば、表の残り全体が候補ごとに展開される。
- 履歴の中のコールは、他の表が既に定義していれば同じノードを再利用する (説明が空なら何も上書きしない)。履歴だけで初めて現れるコールは説明が空の「プレースホルダ」ノードになり、後で同じ位置を定義した行がそれを埋める (§4.8)。
- **末尾の記号が無い履歴行** (`1N-2C`) も履歴である。その後の列 0 の行は履歴の子として読み (上流とは違う。§1.3 の 2)、`ColumnZeroContinuation` (Info) を出す。字下げした行なら Lint は出ない。
- 表の 2 行目以降に `-` か `;` を含むトークンがあると `SequenceNotFirst` (Error) で、その行と部分木を捨てる。

```bml
1N = 15--17 hcp, bal

1N-2C-
2D = no 4 card major
2H = 4+!h
2S = 4+!s, 0--3!h

1N-2C
  3N = 10--15 hcp, to play
```

### 3.5 相手のコールと暗黙パス

- 相手のコールは **括弧** で書く: `(1N)`、`(D)`、`(P)`、`(2Y)`、`(any)`。括弧の無いトークンは我々のコールである。
- 経路の上で **同じ側のコールが 2 つ続くと、その間に反対側のパスを補う** (暗黙パス)。我々のコール 2 つの間には相手の `(P)` が、相手のコール 2 つの間には我々の `P` が入る。したがって競り合いの無い `1N` → `2C` → `2D` は `1N (P) 2C (P) 2D` の 5 コールを表す。
- 暗黙パスはトライの辺を持つが、ノード (行) は持たない。**相手がパス以外のコールをした実際のオークションは、暗黙パスの辺には乗らない**。競り合いのある経路は、相手のコールを明示した表 (`1C-(1S)-` や `1C-(any)-`) で書く。
- 先頭のパスは経路に含めない (§2.6)。表の最初のコールがオープニングである。
- どちらの側のパスでも、実際にそのパスを書いた表でだけ辺ができる。例外はシステム停止 (§7.7) で、停止の後は相手の任意のコールと我々のパスの辺がトライに接がれる。

```bml
1S = 12--21 hcp, 5+!s

1S-(2H)- = 5+!h
3H = !CUE, 10+ hcp, 3+!s
D = 10+ hcp, 0--2!s
P = {prio:-100} any hand

1S-(D)- = t/o, 12+ hcp
2N = !Jordan, 10+ hcp, 4+!s
XX = 10+ hcp
```

### 3.6 アラート印

- 説明文 (最初の行) の先頭の `!` で、直後が小文字の `c`、`d`、`h`、`s` **でない** ものはアラート印である。コールを「アラート対象」(`Alertability::Alertable`) にし、ノードの `flags.artificial` を立てる。印自体は説明文から取り除く。
- `!c !d !h !s` はスート記号 (§5.2) なので、`!s` で始まる説明文はアラート印ではない。スートで始まるアラートは `! !s …` のように `!` と空白を先に書く。
- `!Michaels`、`!TRF`、`!STAY` のような書き方は、アラート印 + 語 (`Michaels` など) である。
- 履歴行の説明文にも同じ規則が働く。

### 3.7 回復規則 (読めない行)

コンパイルはファイル全体では失敗しない。読めない部分は Lint を出して、その部分だけを捨てる。

| 状況 | 扱い | Lint |
| --- | --- | --- |
| コールトークンとして読めない行 | その行と部分木 (より深い字下げの行) を捨てる | `UnknownCallToken` (Warning) |
| 読めない履歴行 | その行と部分木を捨てる | `UnknownCallToken` (Warning) |
| 2 行目以降の履歴形 (`-`/`;` を含む) | その行と部分木を捨てる | `SequenceNotFirst` (Error) |
| 単位と違う字下げ | 最も近い浅い行の子にする | `IndentationMismatch` (Warning) |
| 未知の指示子 | 無視する | `UnknownDirective` (Warning) |
| 相対レベルで始まる段落 | 地の文として読む (中の行は全て失われる) | `UnknownCallToken` (Warning) |

## 4. コールトークン

### 4.1 形の一覧

`calltok` は 1 つのコール (または、コールの集合を表すパターン) を書く。括弧で囲むと相手のコール、囲まなければ我々のコールである (§3.5)。字句は **大文字と小文字を区別する** (`P` はパス、`p` は読めない。`M` はメジャー、`m` はマイナー)。例外は `red`/`black` と `step`/`steps` で、これらは大小を問わない。

| 形 | 例 | パターン (`CallPattern`) | 意味 | 上流 |
| --- | --- | --- | --- | --- |
| `P` | `P`、`(P)` | `Exact(Pass)` | パス | 上流 |
| `D`、`X` | `D`、`(X)` | `Exact(Double)` | ダブル。`X` は拡張 (`NonStandardToken`) | `D` は上流 |
| `R`、`XX` | `R`、`(XX)` | `Exact(Redouble)` | リダブル。`XX` は拡張 (`NonStandardToken`) | `R` は上流 |
| レベル + 1 ストレイン | `1C`、`2D`、`3H`、`4S`、`1N`、`3NT` | `Exact(Bid)` | そのビッド。`N` と `NT` は同じ | 上流 |
| レベル + 複数スート | `2CD`、`3HS`、`4CDHS` | `Strains{level, strains}` | 列挙したスートのどれか。`N` は他のスートと組めない (`2CN` は読めない) | 上流 |
| レベル + `red`/`black` | `2red`、`3black`、`2Red` | `Strains` (D+H / C+S) | 赤 (D、H) / 黒 (C、S) のスート | 上流 (BML 2) |
| レベル + 変数 | `2M`、`3m`、`2oM`、`1X`、`2Y`、`3Z`、`1x` | `Var{level, var}` | §4.2 | 上流 (小文字 `x/y/z` は拡張) |
| 全レベル | `nS`、`nX`、`(nX)` | `Strains`/`Var` (`Level::Any`) | そのストレインの **十分な全てのレベル** (§4.3) | 拡張 |
| 相対レベル | `cS`、`jH`、`cM`、`jY` | `Strains`/`Var` (`Level::Cheapest`/`Jump`) | そのストレインの最も安い十分なビッド (`c`)、その 1 つ上 (`j`) (§4.3) | 拡張 |
| ステップ | `1step`、`2steps`、`3STEPS` | `Step(n)` | オークションの最後のビッドから n 段上のビッド (§4.4) | 上流 |
| 代替 | `2S/3H`、`4D/H`、`P/2C`、`2S/cH` | `AnyOf` | 列挙したパターンのどれか (§4.5) | 拡張 |
| 相手の類 | `(any)`、`(bid)`、`(suit)` | `Class(OppClass)` | 相手の任意のコール / 任意のビッド / 任意のスートビッド (§4.6) | 拡張 |

- `N` と `NT` のどちらでも書ける (`1N`、`1NT`)。スートの文字は `C D H S` の大文字だけ。
- レベルは `1`〜`7` の 1 桁、`n` (全レベル)、`c` (最安)、`j` (ジャンプ)。`8C` や `0C` は読めない。
- トークン全体が読めなければならない。`1Cx` や `2S!` は `UnknownCallToken` (Warning)。
- 字句の試行順は `XX`、`X`、`P`、`D`、`R`、`any`/`suit`/`bid`、ステップ、レベル + ストレイン。レベル + ストレインの中では `red`/`black`、変数、リテラルの順。

### 4.2 変数

| 変数 | 取りうるストレイン | 束縛 |
| --- | --- | --- |
| `M` | H、S | 最初の出現で束縛。以後の `M` は同じスート |
| `m` | C、D | 同上 |
| `oM` | `M` でない方のメジャー | 束縛しない。`M` が束縛済みであること |
| `om` | `m` でない方のマイナー | 束縛しない。`m` が束縛済みであること |
| `X`、`Y`、`Z` (と小文字の `x`、`y`、`z`) | C、D、H、S | 最初の出現で束縛。`X < Y < Z` (C < D < H < S) の順序を保つ |

**束縛の範囲**。変数の束縛は、その表の中で経路 (履歴 + 行の祖先 + その行) に沿って有効である。履歴で束縛した変数は表の全ての行から見え、行で束縛した変数はその行の部分木から見える。兄弟の行は互いの束縛を見ない (兄弟ごとに独立に展開する)。表をまたいで束縛は引き継がれない。

**展開**。未束縛の変数は候補ごとに行 (と部分木) を複製する。候補は次の規則で絞る。

1. **既に使われたストレインを除く**。経路で (どちらの側でも) 既にビッドされたスートは候補にならない。したがって束縛済みの変数どうしは必ず違うスートになる (束縛済みのスートはビッドされているため)。`M` と `X` は別々の変数だが、同じ理由で違うスートになる。
2. **`X < Y < Z` の順序**。束縛済みの変数に対して順序を保つ候補だけを残す (例: `Y` が H に束縛済みなら、新しい `X` は C か D、新しい `Z` は S)。表に `#ANYORDER` があると、その表では新しく束縛する `X`/`Y`/`Z` の順序を外す (異なるスートであることは規則 1 で保たれる)。`#ANYORDER` を書いたのに表が `X`/`Y`/`Z` を 2 つ以上使っていなければ `AnyOrderWithoutVariables` (Info)。
3. **十分なビッドだけ**。新しく束縛する変数は、オークションの最後のビッドより高いビッドになる候補だけを生む (上流の `check_vars` と同じ)。`(1S)-` の後の `2X` は 2C、2D、2H になる (2S はスペードが使用済み)。

束縛済みの変数 (と固定レベル) のコールは候補を絞らない。不十分なビッドになれば `IllegalCall` (Error) でその行を捨てる (同じ行が別の束縛では成功していれば Info に下げる。変数の展開で一部の候補だけが不十分になるのは普通のことだから)。

- 候補の無い新しい変数は `VariableNoCandidate` (Info) で、その行を捨てる。
- 未束縛の `oM`/`om` は `UnboundOther` (Error)。
- 相手の類のワイルドカード (`(any)` など §4.6) の下では、新しい変数は候補を持たない (相手の実際のコールが分からないので、どのスートが使用済みかが決まらない)。

説明文の中の変数は、その行の束縛で置き換わる (§5.3)。

```bml
1M = 12--21 hcp, 5+M

1M-
2M = 6--10 hcp, 3+M
3M = 10--12 hcp, 4+M
2oM = 10+ hcp, 5+oM
```

`1M` は `1H` と `1S` の 2 つのオープニングになり、その下の `2M` は 1H の下では `2H`、1S の下では `2S` になる。1S の下の `2oM` は `2H` だが、1H の下の `2oM` (= `2S`) も十分なビッドなので両方できる。

```bml
(1X)- = 12+ hcp, 3+X
2Y = 10+ hcp, 5+Y
D = t/o, 12+ hcp
```

`(1X)` は相手の 1C、1D、1H、1S の 4 つの表になり、`2Y` はそれぞれ X より高いスートの 2 のビッドだけになる (1S の後は候補が無く `VariableNoCandidate`)。順序を外すと、`Y` は X 以外の全てのスートになる。

```bml
(1X)- = 12+ hcp, 3+X
#ANYORDER
2Y = 10+ hcp, 5+Y
```

### 4.3 全レベル `n` と相対レベル `c`・`j`

- `n` は **十分な全てのレベル** を表す: `nS` はオークションの最後のビッドより高い 1S〜7S の全て。`(nX)-` は「相手の任意のレベルの任意のスートのオープニングの後」である。候補が 8 を超えると `WideWildcard` (Info) を出す (`(nX)` は 28 の表になる)。
- `c` は、そのストレインの **最も安い十分なビッド** (オークションにビッドが無ければ 1 のレベル)。`j` はその 1 つ上のレベル。7 を超える候補は無い (`NoSufficientLevel` (Info) で行を捨てる)。
- 相対レベルは、オークションの最後のビッドが展開時に分かっていることを要する。相手の類のワイルドカード (`(any)`、`(bid)`、`(suit)`) の下で、そのワイルドカードがビッドでありうるときは最後のビッドが決まらないので `LevelWithoutAnchor` (Error) になり、行を捨てる (1 つの範囲につき 1 回)。
- **相対レベルの行で段落を始めることはできない** (§2.2 の規則 6)。相対レベルの行は、表の 2 行目以降か、履歴行の後に置く。

```bml
1H = 12--21 hcp, 5+!h

1H-(1S)-
cH = 6--10 hcp, 3+!h
jH = 0--6 hcp, 4+!h
cN = 10--12 hcp, stopper in !s
```

`1H-(1S)-` の後の `cH` は 2H、`jH` は 3H、`cN` は 1N である。

### 4.4 ステップ

- `<n>step` / `<n>steps` は、オークションの **最後のビッド** (どちらの側のものでも) からストレインの順 (C < D < H < S < NT) で n 段上のビッドである。`1N-2C-` の後の `1step` は 2D、`2steps` は 2H。
- n は 1 桁に限らない (`9steps` も書ける)。
- 最後のビッドが無い、7NT を超える、あるいは相手の類のワイルドカードの下 (最後のビッドが決まらない) では `StepWithoutAnchor` (Error) で行を捨てる。

```bml
2C = 22+ hcp

2C-2D-
2H = 5+!h
  1step = 0--3 hcp
  2steps = 4+ hcp
```

`2C-2D-2H` の後の `1step` は 2S、`2steps` は 2NT である。子の行の位置を履歴で書き直すことはできない。表の 2 行目以降の `-` を含むトークンは `SequenceNotFirst` (Error) で、その行と部分木が失われる。

```bml,should-lint
// expect-lint: SequenceNotFirst
2C = 22+ hcp

2C-2D-
2H = 5+!h
  2H-
  1step = 0--3 hcp
```

### 4.5 代替

- `/` で区切ったパターンのどれか: `2S/3H`、`P/2C`、`(1H/1S)`。
- `/` の後にレベルの無いストレインを書くと、直前のレベルを使う: `4D/H` は `4D/4H`、`2S/cH` の `cH` は相対レベル。
- 各代替は独立に展開される (変数を含む代替では、束縛も代替ごとに違う)。行の説明文は全ての代替に共通である。
- `/` を使うと `NonStandardToken` (Info) が出る (上流では読めない)。

```bml
1S = 12--21 hcp, 5+!s

1S-
3C/3D = 10--12 hcp, 6+ card suit
```

### 4.6 相手の類 `(any)`、`(bid)`、`(suit)`

| トークン | 類 (`OppClass`) | 当てはまる相手のコール |
| --- | --- | --- |
| `(any)` | `AnyCall` | 全てのコール (パス、ダブル、リダブル、ビッド) |
| `(bid)` | `AnyBid` | 全てのビッド (NT を含む) |
| `(suit)` | `AnySuitBid` | NT 以外のビッド |

- トライには 1 本の **ワイルドカードの辺** として入り、実際のオークションでは相手のコールがその類に当てはまれば辿る (§7.1)。同じ位置に相手の具体的なコールの辺 (`(2H)` など) もあれば、具体的な辺を先に試す。
- 類の下の行 (`1S-(any)-` の表の行) は、相手の実際のコールが分からないまま展開する。そのため:
  - 固定レベルのコールは十分性を検査しない (`1S-(any)-` の `2H` は、相手が 3C をしたときには選べないだけで、コンパイルでは Error にならない。実行時に合法性で除かれる)。
  - 新しい変数は候補を持たない (`VariableNoCandidate`)。束縛済みの変数は使える。
  - ステップは `StepWithoutAnchor` (Error)、相対レベルは類がビッドを含むとき `LevelWithoutAnchor` (Error)。
- 類に当てはまるコールがその局面で一つも無い (例: 相手が既にダブルした後の `(any)` は常にありうるが、7NT の後の `(bid)` は無い) 候補は捨てる。
- 類のトークンは括弧で囲むのが正しい書き方である。括弧の無い `any` / `bid` / `suit` も **我々の** 類のコールとして読めてしまう (未定義の動作。段落の分類 §2.2 の落とし穴の原因でもある)。
- 類を使うと `NonStandardToken` (Info) が出る。`(any)` は小文字の `y` を含むので、理由が「小文字の変数 (x/y/z)」とも表示される (履歴行ではその理由だけが表示される)。実害は無い。

```bml
1S = 12--21 hcp, 5+!s

1S-(2H)- = 5+!h
3H = !CUE, 10+ hcp, 3+!s

1S-(any)-
4S = 0--9 hcp, 5+!s
P = {prio:-100} any hand
```

`1S` の後の相手の 2H では `1S-(2H)-` の表が使われ、それ以外の相手のコールでは `(any)` の表が使われる。

### 4.7 相手のコールと我々のコールの間の暗黙パス

§3.5 のとおり、経路の上で同じ側のコールが 2 つ続くと反対側のパスを補う。暗黙パスを補うとき、そのパスが合法でない (オークションが既に終わっている) 候補は捨てる。

### 4.8 同じ位置の複数の定義: 優先順位

同じ経路 (同じオークション) に 2 つ以上の定義が当たるときは、次の規則で決まる。

1. **兄弟の中では Exact 行がパターン行に勝つ**。同じ親の下の兄弟の行は、Exact 行 (`2H`、`P`) を行順に全て展開してから、パターン行 (`2M`、`2X`、`nS`、`2S/3H`、`(any)`) を行順に展開する。パターンの候補が先の Exact 行のコールと同じなら、その候補は捨てて `ShadowedByExact` (Info)。先のパターン行のコールと同じなら黙って捨てる (上流の `bid not in bids_processed`)。
2. **先の定義が勝つ** (表をまたいでも、ファイルをまたいでも)。同じ経路・同じ席とバルの条件の 2 つ目の定義は:
   - 説明が違い、どちらも空でないなら、`DuplicatePath` (Warning) を出して後の定義を捨てる。部分木は先のノードの下に統合される。
   - 先の説明が空 (履歴だけで作られたプレースホルダ) なら、後の説明で埋めて `DuplicatePath` (Info)。
   - 後の説明が空なら、先のノードをそのまま使う (Lint なし。履歴行が既存のノードを辿るのはこの場合)。
3. **席とバルの条件が違う定義は共存する**。それぞれ別のエントリになり、実際のオークションでは **当てはまる条件のうち最も具体的なもの** が使われる。具体性は `席の具体性 × 3 + バルの具体性` で、席は `0` が 0、`12`/`34` が 1、単独の席が 2、バルは `Y`/`N` と指定した側の数 (0〜2)。
   - 条件の違う 2 つの定義が同じ具体性で重なる (両方に当てはまるオークションがありうる) と、`ConditionTie` (Info) を出し、先に入れた方が勝つ。
   - 後から入れた一般的な定義 (`#SEAT 0`) の説明で、先に入れた、より具体的なプレースホルダ (説明が空) を埋める。`DuplicatePath` (Info)。
4. **説明が空の行は、覆う定義を再利用する**。説明の無い行 (履歴や中継の行) は、同じ経路のより一般的な条件の既存のノードがあれば、新しいノードを作らずにそれを使う。

```bml
1N = 15--17 hcp, bal

#SEAT 34

1N = 14--16 hcp, bal

#SEAT 0

1N-
2C = !STAY, 8+ hcp
```

この例では、3 席目・4 席目の 1N は 14--16、それ以外は 15--17 である。`1N-` の表 (`#SEAT 0`) は両方の 1N の後に効く。

```bml,should-lint
// expect-lint: DuplicatePath
1C = 12--21 hcp, 3+!c
1C = 16+ hcp
```
